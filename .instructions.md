# Інструкції для розробки проєкту Headless Orchestrator

## Загальні принципи
- Архітектурні рішення, пояснення та документація ведуться українською мовою.
- Код має бути придатним для продакшну та B2B SaaS-сценаріїв.
- Мінімізувати технічний борг: чіткі контракти між модулями, типобезпека, передбачуване завершення ресурсів.

## Стандарти для Rust (`core/`)
- Обов'язкова асинхронна архітектура на базі `tokio`.
- Централізована обробка помилок через `anyhow` та/або `thiserror`.
- Категорично заборонено використання `.unwrap()` у продакшн-коді.
- Кожен Chromium child-process має гарантовано завершуватися при штатному/аварійному завершенні сервісу.
- Обов'язковий захист від зомбі-процесів: моніторинг стану дочірніх процесів, таймаути graceful shutdown, примусове завершення за потреби.
- Ізоляція профілів/кешу браузера для сесій має бути явною та керованою.

## Стандарти для Python (`sdk/python/`)
- Цільова версія Python: 3.10+.
- Обов'язкові сучасні type hints для публічних API.
- Підтримка `asyncio` у клієнтському SDK.
- Транспорт взаємодії з оркестратором через `websockets`.
- Інтерфейс SDK має бути ергономічним для інтеграції в automation pipelines.

## Вимоги до якості
- Пріоритет безпечної деградації: помилки мають бути інформативними, а ресурси — вивільнятися гарантовано.
- Важливі архітектурні компроміси мають супроводжуватись короткими ADR-поясненнями в README або модульних док-коментарях.
