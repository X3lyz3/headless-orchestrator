# Development Instructions for the Headless Orchestrator Project

## General Principles
- Architecture decisions, explanations and documentation are written in English.
- Code must be production-ready and suitable for B2B SaaS scenarios.
- Minimize technical debt: clear contracts between modules, type safety, predictable resource cleanup.

## Rust Standards (`core/`)
- An asynchronous architecture based on `tokio` is mandatory.
- Error handling is centralized through `anyhow` and/or `thiserror`.
- Using `.unwrap()` in production code is strictly forbidden.
- Every Chromium child process must be guaranteed to terminate on both normal and abnormal service shutdown.
- Zombie-process protection is mandatory: monitor the state of child processes, apply graceful-shutdown timeouts, and force termination when needed.
- Isolation of browser profiles and cache between sessions must be explicit and controllable.

## Python Standards (`sdk/python/`)
- Target Python version: 3.10+.
- Modern type hints are mandatory for public APIs.
- The client SDK must support `asyncio`.
- Communication with the orchestrator uses `websockets` as the transport.
- The SDK interface must be ergonomic for integration into automation pipelines.

## Quality Requirements
- Safe degradation is a priority: errors must be informative, and resources must always be released.
- Important architectural trade-offs must be accompanied by short ADR-style explanations in the README or module-level doc comments.
